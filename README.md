<h1 align="center"><img src="assets/logo.svg" alt="hashira" width="360"></h1>

**Coupling, cognitive-complexity, duplication and design-smell analysis for Ruby, read from the AST with [Prism](https://github.com/ruby/prism).**

hashira tells you which file to open first. It reads a codebase four ways —
which packages depend on which, how hard each method is to follow, what has
been copied, and which objects reach into each other — ranks files by cost
against how often they change, and ratchets every finding in CI, so a build
fails on what *this commit* made worse rather than on a score.

- **Precision first.** A finding is advice: move this method, split that flag,
  cut this edge. hashira reports one only where the advice applies to code you
  own. A library's AST node, a public argument, a core collection are not yours
  to redesign, so they are left alone. Each smell section below says what is
  left alone and why.
- **No runtime dependencies.** Prism ships with Ruby 3.4+. What Ruby itself
  defines (core classes, the standard and bundled libraries, `Kernel`'s
  methods) comes from a generated inventory, never from whatever the running
  process happens to have loaded, so two runs on the same code agree.
- **Four analyzers, opt-out.** `--skip` drops any of coupling, complexity,
  duplication and smells.
- **Made for CI.** A committed baseline ratchets edges *and* findings, with
  magnitudes; `--fail-on` gates outright; a `# hashira:` comment silences one
  finding, with a mandatory reason that the report repeats.

Let `billing` and `shipping` reference each other, and hashira names the cycle
and the cheapest edge to cut:

<!-- example: cycle app -->
```console
$ hashira app
Package (folder) metrics for app  (2 packages, 2 files)

package   TC  Ca  Ce     I  Cyc
-------------------------------
billing    1   1   1  0.50  YES
shipping   1   1   1  0.50  YES

Findings (1):
  cycle: billing and shipping depend on each other in a cycle — any change may ripple back around. The cheapest cut is billing -> shipping (1 ref).
      · billing/client.rb:5: Shipping::Rate
```

A healthy project reports `Findings (0): none ✓ — structure is healthy`.

Every console example in this README is run by the test suite against a
fixture, so what you read is what hashira prints.

## Install

```sh
gem install hashira          # or, in a Gemfile: gem "hashira", group: :development
```

Requires Ruby 3.4 or newer.

## Running it

```sh
hashira                        # auto-detects each lib/<gem>, or app + lib in a Rails root
hashira lib/myapp              # one directory
hashira app lib                # several — one shared graph
hashira --skip complexity      # drop an analyzer
hashira --kind cycles,smells   # keep only these findings (tables stay whole)
hashira --top 50               # longer tables and findings list
hashira --only app/models      # report only findings in these files; still reads everything
```

With no directory, hashira picks every `lib/<gem>` that sits beside a
`lib/<gem>.rb` (rubygems holds two: `lib/bundler` and `lib/rubygems`), each
with its entry file (`lib/<gem>.rb`, shown as `../<gem>.rb`), else `lib`; with
no code in `lib/`, the
folders the gemspec's `require_paths` lists or globs (fastlane's
`Dir["*/lib"]` is nineteen gems); and in a Rails root (a
`config/application.rb`) `app` and `lib`. One directory is descended through
single-folder wrappers, so `hashira`, `hashira lib` and `hashira lib/gem/core`
land on the same packages. With one directory files are named relative to it;
with several, as you would open them from where hashira runs. The entry file of
a library hashira narrowed to (`lib/rack/attack.rb` beside `lib/rack/attack/`)
is named from the project's root. Templates a
generator copies into an app (`lib/generators/**/templates/`), and the
overrides Rails reads from `lib/templates/`, are not the
project's code and are left out. Nor is a project template a gem ships below
`lib/` to copy into a new project: a folder named `templates` or `*_template`
that holds template or project files (an `.erb` or `.tt`, a `Gemfile`, a
gemspec, a `Rakefile`), such as bridgetown's `lib/site_template/`; a folder of
plain Ruby by that name (`lib/yard/templates/`) is code. Nor is vendored or
generated code: a file under a `vendor/` folder below the analyzed directory,
or a `.rb` that a grammar beside it generates (a sibling `.rl`, `.y`, `.racc`,
`.treetop` or `.rex`) or whose leading comments, before its first line of
code, say so ("generated by", "generated from", `@generated`,
"auto-generated", "a generated file", "do not edit", "DO NOT MODIFY", "has
been generated"); a comment after the first line of code never marks a file.
hashira says on stderr how many files it analysed and how many of each kind it
skipped; name the vendored or template directory, or `--only` a file, to
analyse it anyway.

A Rails engine is a Rails app: a project with no `config/application.rb` whose
`lib/` holds exactly one engine — a `< Rails::Engine` class or an
`isolate_namespace`, in any file (camaleon-cms, a gem's `lib/<gem>/engine.rb`,
devise's `lib/devise/rails.rb`) — gets the Rails handling for its `app/` —
namespace packages, Zeitwerk folder namespaces, associations, the framework's
dead-code roots — while its `lib/` keeps a library's dead-code roots (its
public surface is the host app's API), and it is
packaged by the classes under the engine's module (`CamaleonCms::Post` is the
`Post` package), not as one package named after it. A repository holding several
engines (rails itself) is read as libraries.

The text report is the coupling tables, the complexity tables, the hotspot
rollup and the findings, capped at 25 packages and findings and 10 methods and
files; every capped list says what it withheld, and `--top N` moves every cap.
Findings are dealt out across kinds, worst first within a kind, structural
kinds (cycles, layers, dead code, associations) before the design smells and
the local ones (`repeated_call`, `duplication`) last, and a capped list opens
with one line per kind, so hundreds of findings of one kind read as
one fact. Anything hashira had to work around (no git history, a shallow clone,
a file Prism could not parse) goes to stderr. A shallow clone, or a history of
fewer than two commits, ranks the hotspots by cost alone and leaves
change_coupling nothing to judge, and the stderr line says so:

```text
hashira: shallow git history (1 commit) for lib — hotspots are ranked by cost alone; change_coupling cannot judge
```

and the findings list, where a run with no findings would call the structure
healthy, names what went unjudged (`none — change_coupling could not judge:
shallow git history (1 commit)`, or `none ✓ for the kinds judged;
change_coupling not judged (…)` beside kinds that were judged); `--json` lists
them under `unjudged`.

## Configuration

A `.hashira.yml` holds the flags you would pass every time, each key a flag
without its dashes, plus `directories`, `checks`, `layers` and `boundaries`
(an [interpreted model](#ci) you declare):

```yaml
directories: [app, lib]
skip: duplication
fail-on: cycles
package-by: namespace
checks:
  duplication: false               # turn a kind off
  middle_man: true                 # or an opt-in kind on
  complexity: { threshold: 12 }    # or move a threshold
  fragmentation: { helpers: 6 }    # fragmentation has two limits
  indirection: { threshold: 3 }    # (a setting turns an opt-in kind on too)
layers: [web, app, domain]         # outermost first; see Layers below
strict: true                       # the strict set; see Strict below
```

`checks: all` turns every kind on. Kinds with a threshold, and what reaches it:
`complexity` (a score of 10 or more), `fragmentation` (`helpers:` 4 or more,
averaging `lines:` 3.5 or fewer), `indirection` (2 or more hollow helpers),
`boundary_sprawl` (12 or more methods), `wide_edge` (5 or more constants),
`state_sprawl` (a weight of more than 4), `repeated_conditional` (more than 2
tests), `low_cohesion` (classes of 6 or more methods) and `middle_man` (3 or
more forwarders). `change_coupling` takes `commits:`, `degree:` and `files:`,
and `dead_code` takes `roots:` (see [whole-codebase checks](#whole-codebase-checks)).
`checks: { all: true, nil_check: false }` turns every kind on but the ones
it names. A flag on the command line wins over
the file, and a key the command line rules out sits that run out (`fail-on` under
`--json`). `--config PATH` reads another file; `--no-config` ignores it.

### Which kinds are on by default

A kind is on by default when hashira reads the facts behind it correctly and
its advice is the philosophy's: objects that own their state and behavior, no
nil passed around, no type switches, no dead weight, no reaching through other
objects. Whether Rails or idiomatic Ruby agrees is not a criterion: a habit a
framework makes easy (an association chain, a nil-tolerant reader, a callback
that sets state) stays a finding. A contract a framework dictates (a hook it
calls by name, a constant it reads) is not the project's to redesign and is
left alone.

Volume is not a reason to switch a kind off. It is handled by grouping, so a
finding is one thing to fix — one `nil_check` per nil source with every check
of it as evidence, one `message_chain` per pair of classes reached through, one
`fragmentation` per knot of helpers — and by the [ratchet](#ci), which records
what is there today and fails only on what gets worse.

So everything is on but five kinds:

| kind | why it waits for you |
| --- | --- |
| `middle_man` | forwarding is what `message_chain` asks for; turn it on to find classes that only forward |
| `indirection` | a thin named step is what an explanatory helper is; `fragmentation` reports the knots that hurt |
| `repeated_conditional` | `manual_dispatch` already reports the type and status switches, a type test repeated across methods included; what is left, plain value tests, may be fine |
| `boundary_sprawl` | an interpreter of a foreign model is legitimate; declare the ones you mean (see [CI](#ci)) |
| `change_coupling` | needs the git history, which a shallow CI checkout lacks |

`layer_violation` is on whenever `layers:` are declared. `--kind` and
`--fail-on` turn on the kinds they name (`--fail-on all` names none: it gates
what the run checks; a [strict](#strict) kind waits for `strict: true`), and a
`checks:` setting for a kind turns it on. `--kind`
also turns the others off for that run, so a design smell nobody asked for is
never computed.

The earlier policy switched kinds on by a precision measured on labels. Those
labels are in [eval/results](eval/results/README.md): two independent AI
raters, version-blind, on rubocop, faraday and rubygems.org, judging whether a
strict reviewer would ask for the change. Most false labels were misreads —
a library's contract, a public argument, a coincidental shape, a remedy with no
owned destination — and the rules have since stopped reporting those; the
field test on ten Ruby and Rails codebases fixed the rest it found. The labels
stay as the regression record for what hashira must not report.

hashira finds the file, and the baseline, in the analyzed project's root: the
nearest folder at or above the analyzed directory that is where hashira runs or
holds a `.hashira.yml`, a `hashira_baseline.json`, `.git`, a `Gemfile` or a
`*.gemspec`. A project checked out inside another stops at its own root. So `hashira ../other/lib` reads and writes the other project's
files, not the ones where you stand. Paths inside the file are read from that
root.

### Strict

`strict: true` in `.hashira.yml`, or `--strict` on the command line, turns on
the strict set: one more kind and stricter readings of four kinds that are on
by default. Without it a run reports what it reported before they existed,
under `checks: all` too, so upgrading hashira adds no finding to a codebase
that gates on zero. Each follows the philosophy; they wait because they are
new and report code that passed before.

| kind | what strict adds |
| --- | --- |
| `stateful_mixin` | the kind: a mixin that works on its host's state instead of decorating it |
| `nil_check` | a parameter the method defaults to nil and tests; the answer of another owned class's method that can answer nil, named for that method |
| `concrete_inheritance` | under a framework root, a subclass overriding a working method of its concrete parent (single-table inheritance); a class extending `Array`, `Hash`, `String` or `Set`; a `Base…` parent read as abstract |
| `low_cohesion` | models: the framework exemption narrows to controllers, mailers, jobs, channels and mailboxes |
| `data_class` | a bare `Struct` or `Data` value, or a record with no behavior, that another class computes with |

`checks: { stateful_mixin: true }` turns that kind on by itself, without the
readings. `--kind` and `--fail-on` do not: `--fail-on smells` names every
smell, and would otherwise turn it on.

### Suppressing one finding

A comment silences the findings of the kinds it names, on its own line
(`hashira:disable`) or on the next one (`hashira:disable-next-line`). The
reason after `--` is required:

<!-- example: suppressed lib/shop --kind complexity -->
```console
Findings (0):
  none ✓ — structure is healthy

Suppressed (1):
  ~ complexity/Shop::Pricing#total — legacy rules, rewrite scheduled (pricing.rb:3)
```

from

```ruby
# hashira:disable-next-line complexity -- legacy rules, rewrite scheduled
def total(order)
```

A finding is matched by any line it names (a method's `def`, each site of a
clone), so one directive can sit beside the copy you mean. A directive that no
longer silences anything is listed as unused, and a malformed one (no reason,
an unknown kind) stops the run with its file and line.

## Coupling

Every folder under the analyzed directory is a **package**:

- **TC** — classes and modules it defines (a namespace wrapper with no methods
  does not count).
- **Ca** / **Ce** — how many packages depend on it, and how many it depends on.
- **I** — instability, `Ce / (Ce + Ca)`: 0 is a foundation everyone leans on, 1
  is free to change. Neither is good or bad; the findings are about arrows that
  point the wrong way.

An edge A→B exists when a file in A references a constant B declares,
resolved the way Ruby resolves it: lexical nesting first, then the innermost
class's ancestors, then top level. `Billing::Client` inside `module Shipping` is
not `Shipping::Billing::Client` unless that exists. Ruby's own constants never
belong to a package, even where the project reopens them, and neither does a
namespace a dependency owns: a gem's whole camelized name in
`Gemfile.lock`, the `Gemfile` or a gemspec (`devise` → `Devise`,
`travis-config` → `Travis::Config`), or the path the `Gemfile` requires it by
(`require: "shop/sql"` → `Shop::Sql`), unless it sits under one of the project's
own gems. A gem never claims a root by its first word: `travis-config` leaves
`Travis` to the project that defines it, and `rubocop-rails` claims
`RuboCop::Rails`, while `RuboCop` is foreign because `rubocop` is a gem too.
A root the project's own `require` paths name, where no folder or file of the
project does, is a dependency's (`require "gds_api/publishing_api"` →
`GdsApi`). Names are matched as Ruby spells them: where the project opens a
root and also reads a differently spelled twin it never opens (its own `module
Omniauth` beside the gem's `OmniAuth::Strategies::OpenIDConnect`), the opened
spelling is the project's, whatever gem name folds to it. A
reopened core class (``class ::Array < `Array` ``, `class String < Object`) stays
Ruby's whatever superclass it spells. Any other top-level
namespace is the project's only where the project opens it with definitions
(`module Shop` holding a class, a method or a constant, not just `autoload`s),
or where Zeitwerk makes it of a folder; a file path that names it, or a class
the project derives under it, does not claim it — the derived class itself is
the project's. A constant that aliases something other than a class body the
project defines (`ParentClass = cond ? A : ActiveRecord::Base`) leaves the
project, so a class built on it keeps the framework's exemptions. Each edge
carries a weight, the number of references behind it.

Findings:

- **cycle** — packages that can all reach one another, reported once per knot
  with its **cheapest cut**: the set of edges of least total weight whose removal
  leaves no cycle (a minimum feedback arc set). Among cuts of the same weight
  it keeps the edges into the packages more others depend on (the higher Ca)
  and cuts the ones out of them, so the package everything rests on stays at
  the bottom. It is exact for knots of up to twelve packages; beyond that it is
  a heuristic, and the message says "the cheapest cut found". The evidence is
  the references on those edges — the lines to change.
- **unstable_dependency** — a stable package depends on a less stable one, against
  the Stable Dependencies Principle. It needs a gap of at least 0.10 and three
  edges at each end; edges inside a cycle are the cycle's.
- **mixed_audience** — a package whose constants split into parts that disjoint
  sets of clients use: separate packages in disguise. The finding names the seam
  and any shared base layer.
- **wide_edge** — one package reaching into another through five or more
  distinct constants; a facade would narrow it to one.
- **roll_call** — the same list of three or more words maintained by hand in
  three or more files across packages; the list wants a single owner.

## Whole-codebase checks

These checks read the whole codebase at once: the layering you declare, the
code nothing reaches, and the files that keep changing together.

### Layers

Declare the layers in `.hashira.yml`, outermost first. Each is a package name,
or a name with the packages and paths (from the project's root) it holds:

```yaml
layers:
  - web: [app/controllers, app/views, app/helpers]
  - app: [app/jobs, app/services]
  - domain: app/models
```

In a Rails app, `layers: rails` declares the conventional three: `web`
(`app/controllers`, `views`, `helpers`, `components`, `serializers`,
`presenters`, `decorators`, `policies`, `avo`, `dashboards`, and the other
delivery mechanisms: `mailers`, `mailboxes`, `channels`, and mailer previews
wherever they sit: `**/mailers/previews/**`, `*_preview.rb`), `app` (`app/jobs`,
`workers`, `services`, and every other `app/` folder: `forms`, `queries`,
`wizards`, …) and `domain` (`app/models`, `app/validators`, `lib`). A model that
enqueues a job or sends mail from a callback then points outward, which is the
point. The finding never proposes an order that puts the preset's `app` below
its `domain`.

A layer may use the layers declared inside it, never one outside it.
**layer_violation** reports every reference that points outward, one finding
per pair of layers, with the class edges to cut (the class that refers, the
class it names), the cheapest first:

<!-- example: layers app --kind layer_violation -->
```console
Findings (1):
  layer_violation: billing depends on web, an outer layer, through 1 ref — a layer may depend only on the layers declared inside it. Cut Billing::Ledger -> Web::InvoicesPage (1 ref).
      · billing/ledger.rb:5: Web::InvoicesPage
```

A file is in the layer whose path holds it or whose package it charges, a
constant in the layer of the files that define it (one defined in two layers is
left alone), and a file in no layer is not judged: hashira says on stderr how
many files sit in no layer, and in which folders. The ratchet holds a pair by
its count of references, so a new one fails the build. When the code leans the
other way (another order of the same layers, found by the same exact search as
a cycle's cheapest cut, would leave fewer references pointing outward), the
finding says so, naming that order, which keeps yours wherever the references
leave it free: the declaration may be what is wrong. With no `layers:`, the
check does nothing; declared, it is on, since the intent is yours.

### Dead code

**dead_code**, on by default, reports methods and constants defined in the project that
nothing in it reaches. A constant is reached when the constant-reference graph
resolves a reference to it or to anything inside it; a method when any call,
symbol or string in the project names it (`send(:name)`, `before_action
:name`, `respond_to?(:name)`, a `delegate`, a string `class_eval`), when a
call builds its name from a literal prefix (`public_send("on_#{event}")`
reaches every `on_` method), or when a word in the project's other files names
it: views, rake tasks, configuration, scripts, a gem's README and
`docs/**/*.md`. In a spec or test file only a call, a symbol or a constant
counts (`.name`, `name(`, `:name`, `&:name`, `Name`; `be_valid` reads as
`valid?`, `have_items` as `has_items?`), not a `let` or a local that happens to
share the name. Matching is by name, not
by type, so a method called anywhere under its name counts as used: hashira
misses dead code rather than report live code. Also left alone:

- Ruby's protocols and hooks (`to_s`, `each`, `==`, `call`, `initialize`,
  `inherited`, `method_missing`, `as_json`, Ruby 4.0's
  `instance_variables_to_inspect`, ActiveModel's `use_relative_model_naming?`,
  …) and a method that calls `super`,
  which overrides something its caller reaches.
- Every method of a class that sends itself a computed name (`send(name)`), and
  of its descendants.
- Subclasses registered through an `inherited` hook or found with
  `.subclasses` or `.descendants`.
- A `ClassMethods` module, and the public methods and constants of a class
  whose ancestry leaves the project (`< ActiveRecord::Base`, a parent computed
  by a call, `< Pay.model_parent_class.constantize`, `include
  Sidekiq::Job`, Administrate's `ATTRIBUTE_TYPES`) or of a module mixed into
  one: the framework calls them. So are a private method of such a class, which
  may fill the library's template hook (`RuboCop::Runner#file_finished`), or of
  a module such a class includes (solid_cache's `Store::Api#read_multi_entries`,
  which ActiveSupport's `Cache::Store#read_multi` calls), an override of such a
  hook in a subclass however deep (dry-monads' `TupleConstructor#open_token`
  under `RegularConstructor`'s), and the override points frameworks document by name (Devise's
  `active_for_authentication?`, FriendlyId's `should_generate_new_friendly_id?`,
  a routing constraint's `matches?`).
- A module handed to a library from outside its own body (`Lib.prepend(M)`,
  `register_filter(M)`), resolved the way Ruby reads the name where the call
  sits (`Host.include Extension` inside a namespace), or from inside it
  (`ActionDispatch::Routing::Mapper.include(self)`); a class or module whose
  body runs code at load (a hook registration such as
  `Warden::Manager.after_set_user`); and every constant a computed `const_get` can reach
  under its receiver, the constant-world twin of `send(name)`. A name built
  around a literal (`"#{kind}Presenter".constantize`, `:"#{a}_sql"`) reaches
  every constant or method that ends, or starts, with the literal.
- A class the project reopens but [leaves to its owner](#coupling): Ruby's
  (`class String`), or one opened in a library's namespace
  (`class ActionText::Content::Filters`) that the project does not otherwise
  claim. References to it never resolve to the project, so they cannot show it
  is used. The methods the project adds to Ruby's classes are still judged; the
  ones it patches into a dependency's namespace (`Rack::PageCaching::Utils.gzip_level`),
  or into a module it includes, prepends or extends into a dependency's class
  (`SSHKit::Backend::Netssh.prepend(Limit)`, a plugin's
  `app.send(:include, InstanceMethods)`), are that library's to call. A block a
  constant evaluates (`Rack::Request.class_eval do … end`, `module_eval`,
  `class_exec`, `module_exec`), and a `Module.new do … end` it includes or
  prepends, open that constant: their methods are its, and a patch when it is
  a dependency's.
- A constant reached through a computed scope (`journey::SlugSequence`,
  `presenter::SEARCH_FIELDS`, `self.class::KIND`): every owned constant of that
  name counts as used.
- Every constant of a namespace an `eval`, `class_eval`, `module_eval` or
  `instance_eval` string with an interpolation runs in, which may name any of
  them (kaminari's `eval "… #{tag.classify}.new …"` inside
  `Kaminari::Helpers::Paginator` builds `FirstPage`); the top level is not such
  a namespace. A plain string's words count like any other.

The roots differ by kind of project. In a library, every public method and
public constant is its users' API, so only private methods and
`private_constant`s are judged. In a Rails app, controllers, helpers, views,
jobs, mailers, channels, policies, components and validators are the
framework's entry points, and everything else is judged. `roots:` names more:
constants (`MyGem::CLI`, with everything inside), methods (`MyGem::CLI#run`)
and paths (`lib/my_gem/plugins`). In a library, naming roots says what the API
is, and the rest of the public surface is judged too.

<!-- example: dead lib/app --kind dead_code -->
```console
Findings (1):
  dead_code: Invoice#legacy_total is never called in the project (invoice.rb:8). Delete it, or name it in dead_code roots if code outside the project uses it.
```

### Change coupling

**change_coupling**, opt-in, reads the git history behind the hotspots: two files in
different packages that changed together in at least `commits:` 5 commits, and
in at least `degree:` 50% of their changes (shared commits over the mean of
the two files' commits, Tornhill's degree of coupling). Commits touching more
than `files:` 30 analyzed files (a rename, a style sweep) are not counted. The
finding says whether one file refers to the other: a pair with no reference
between them is coupled where the code does not show it.

It needs the history: a CI checkout of one commit (`actions/checkout`'s
default) sees none. In a shallow clone change_coupling reports nothing, says so
on stderr, and stays out of `--fail-on all`; a ratchet there would still find
the recorded pairs resolved. Fetch the history (`fetch-depth: 0`) wherever
change_coupling is gated.

## Rails apps

Layer folders are framework layout, not architecture, so when the analyzed
directory is or sits in a Rails root, hashira groups types by top-level
constant instead (**namespace packaging**), and asks whether `Billing` reaches
into `User`:

<!-- example: rails app -->
```console
$ hashira app
Package (namespace) metrics for app  (4 packages, 4 files)

package            TC  Ca  Ce  I     Cyc
----------------------------------------
Billing             1   2   1  0.33  -
User                1   1   1  0.50  -
(web)               1   0   1  1.00  -
...
Findings (1):
  bidirectional_association: User and Billing::Invoice each declare an association to the other (models/user.rb:2) — navigating both ways ties them together. Drop User's side and query Billing::Invoice where it is needed.
      · models/user.rb:2: has_many Billing::Invoice
      · models/billing/invoice.rb:3: belongs_to User
```

- **Associations are references.** `belongs_to :user` refers to `User` and
  `has_many :line_items` to `LineItem`, inferred with ActiveSupport's inflection
  rules, including the app's own `config/initializers/inflections.rb`; an
  explicit `class_name:` wins and `polymorphic: true` names nothing.
- **Two-way associations are their own finding.** When `User has_many :posts`
  and `Post belongs_to :user`, each model declares the other. That pair is not
  code reaching back, so it stays out of the cycle search and the stability
  check: a cycle means a method, a constant or a one-sided association closes
  the loop. It is still
  two classes that know each other, and **bidirectional_association** reports
  it: one finding per owning model, naming every model it is navigated both
  ways with ("Edition is navigated both ways by 9 models"), each by its class
  even inside a namespace package. Drop the owning side (`has_many`,
  `has_one`) and query the other where it is needed. A pair whose code also reaches both ways is in the cycle
  search as well.
- **Dropping a side can drop a guarantee.** `has_many :posts, dependent:
  :destroy` is more than a reference: deleting the user deletes the posts (or
  nullifies them, or refuses). When the side to drop, or an edge to cut, carries
  a `dependent:` option, the finding names it, and the JSON lists it under
  `guarantees`. Move the guarantee first: to an object above both, or, for
  `:delete_all` and `:nullify`, to the foreign key's `on_delete`. A foreign key
  cannot stand in for `:destroy`, which runs the records' callbacks.

<!-- example: cascade app --kind bidirectional_association -->
```console
$ hashira app --kind bidirectional_association
...
Findings (1):
  bidirectional_association: User and Post each declare an association to the other (models/user.rb:2) — navigating both ways ties them together. Drop User's side and query Post where it is needed. It carries has_many :posts, dependent: :destroy: hand that to an object above both, or to the foreign key, first.
      · models/user.rb:2: has_many Post
      · models/post.rb:2: belongs_to User
```

- **Framework adapters are plumbing.** A top-level class that extends an outside
  class and that the app's classes extend (`ApplicationRecord <
  ActiveRecord::Base`, a `ApplicationCable::Channel`) is not a package anyone
  depends on, however its heirs spell it (an engine's `Pay::ApplicationRecord`).
  A domain base class (`Billing::Base`) stays part of its domain, and so does a
  record straight on `ActiveRecord::Base` that neither says it is abstract
  (`self.abstract_class = true`, `primary_abstract_class`) nor is named
  `Application…`: its subclasses are single-table kinds of it (mailboxer's
  `Message < Notification`).
- **Presentation stays out of the domain.** Controllers, serializers and
  resources are one `(web)` package, counted once as a client of each package it
  uses.
- **Tests stay out of the structure.** Analyzed, the files under the app's
  `test/` and `spec/` are one `(test)` package: it depends on what it tests but
  is no package's client. A test named into a domain's namespace
  (`WebPush::ConnectionsTest`) and the helpers it includes never join that
  domain's cycles, SDP, audience or wide-edge findings, and never add to a
  package's Ca.
- **Folding.** A package that is part of another joins it, and every fold is
  listed: `base` (a lone class joins its superclass's package), `suffix`
  (`OrderPolicy` joins `Order`), `plural` (`Orders` joins `Order`), `mixin` (a
  module that only includes another).

`--package-by folder` or `--package-by namespace` forces either grouping
anywhere.

## Complexity and fragmentation

Every method gets a **cognitive complexity** score, per the
[SonarSource specification](https://www.sonarsource.com/docs/CognitiveComplexity.pdf):
straight-line code is free, each `if`, loop, `case`, `rescue` and ternary costs
one plus its nesting, `else`/`elsif` cost one, a run of one boolean operator
costs one, and recursion costs one. Blocks and lambdas nest what they hold, a
method defined with `define_method` is scored like any other, and parentheses
do not split a boolean run. **Calls** sits beside it: when the two disagree,
Cog is the one that tracks reading effort. A per-class rollup keeps a class's
total visible after a method is split into five.

Methods at or over 10 are `complexity` findings, with where the points came
from:

<!-- example: complexity lib/shop --kind complexity -->
```console
Findings (1):
  complexity: Shop::Pricing#total — cognitive 11, 14 calls (pricing.rb:3). flatten the branching — guard clauses, early returns, or polymorphism.
      · if +6 (lines 4, 5, 6)
      · elsif +2 (lines 8, 14)
      · else +1 (line 10)
      · boolean +2 (line 14)
```

Splitting a method into helpers lowers every score, and past a point it stops
helping the reader, who now hops between many small methods to follow one piece
of work. **fragmentation** reports an entry, a public method, that reaches four
or more methods of its own class along a path at least two deep, when the entry
and every method it reaches average three and a half lines or fewer (blank and
comment lines aside, a heredoc's lines in). Named predicates (`deferred?`,
`alone?`) are left out of the count: readers keep them as meaning, so the
finding lists them as not counted. A helper that a subclass overrides is a
template hook, not a fragment, and ends the path. A method reaches another by calling it with
no receiver or on `self`, or by `send(:name)` and `method(:name)`; instance
methods reach instance methods and class methods class methods, across every
file that reopens the class.

<!-- example: fragmentation lib/app --kind fragmentation -->
```console
Findings (1):
  fragmentation: Report#render spreads its work over 7 private helpers only it calls, averaging 1.0 lines a method, 3 deep (render → body → lines → line) (report.rb:4). Merge the helpers that only move data into the entry; keep named predicates.
      · title (line 8)
      · label (line 10)
```

The limits come from a blind readability study
([eval/results/fragmentation](eval/results/fragmentation/README.md)): two
raters read 60 entry methods with their helpers, half from two codebases
written in this many-tiny-methods style and half from rubocop, faraday and
rubygems.org, then 60 fresh ones. The rule was set on the first sample. On the
second it flagged 10 entries once predicates were left out of the count; one
rater or both judged 9 of them over-fragmented, and both raters 8. The raters were independent AI reviewers,
separate model instances that saw only the shuffled items, not their sources or
hashira's code; no human has rated them yet.

A helper can also add nothing at all: a private one-liner, called once, that
only passes a call on. The reader still makes the hop. **indirection**, opt-in,
counts those hollow hops. A helper
is hollow when it is private, called exactly once from its own class (never by
name, `send`, or through a receiver), and its body is one call with no decision
and no block, wrapping at most one more call (`def import(rows) =
persist(rows.compact)`). hashira follows each method's single-use helpers and
reports the path holding the most hollow ones once it holds two:

<!-- example: indirection lib/app --kind indirection -->
```console
Findings (1):
  indirection: Importer#run reaches its work through 2 hollow helpers, private one-liners called once that only pass a call on (importer.rb:4). Inline them into their callers.
      · import (line 8)
      · persist (line 10)
```

A helper that decides, computes or runs several statements is the decomposition
you want: it costs nothing and the path runs on through it. A helper two
methods share, or a public one, is an abstraction and ends the path.

## Duplication

Copies of one thing collapse into one finding with every site, and the advice
says what varies between them:

<!-- example: duplication app --kind duplication -->
```console
Findings (1):
  duplication: 3 similar fragments (mass 38) — differs only in literal values — extract a method, pass them as arguments.
      · reports/orders.rb:4-8
      · reports/payouts.rb:4-8
      · reports/refunds.rb:4-8
```

Candidates are every run of one to twelve sibling statements, and every method,
`rescue` clause and `when` arm whole. Exact copies match by shape. Near misses
— a renamed variable, an extra line — are compared only between whole methods,
clauses and arms, and need two things: their node types must share at least 80%
of a longest common subsequence, and the names they use (calls, constants, and
the words in their strings and symbols) at least half. Two methods of one shape
that call different things or say different things are not clones. Candidates
are indexed by their rarest node types; a crowded bucket is split by MinHash
bands over those names rather than skipped.

What is not counted:

- **Lists and declarations.** A run of identically shaped statements (requires,
  routes, registrations, the rows of a keyword table, whose literal lists may
  differ in length), a `case` of three or more same-shaped arms, a class
  body of macros with literal arguments (`has_many`, `validates`, `attribute`),
  constants holding literals or frozen lists of constants, and a constructor
  that only stores its arguments.
- **Error reporting.** A log line (a Logger severity sent to something named
  `log` or `logger`) and a call that hands on the rescued error
  (`rescue => e; Sentry.capture_exception(e)`) weigh nothing as a lone statement,
  and a `rescue` clause that only reports its error weighs nothing wherever it
  sits. A report that builds its own context outside a rescue is code.
- **Calls into an abstraction you already have.** `def patch(path, body) =
  request(:patch, path, body)` beside `def post` is already factored: a method
  whose body is one call to a method the project defines, and whose copies
  differ only in what they hand it, block included (`meanwhile(email, name) {
  boost(message) }`). A test block (`test "..." do`, `it`, `specify`) counts
  as such a method, its name included in what may differ. What the block holds
  is still compared on its own, so copies inside it are a clone.
- **Inverse pairs.** `lock!`/`unlock!`, `enable_x`/`disable_x` share a shape by
  design.

A smaller clone inside a bigger one is reported only when two of its sites lie
outside it. The mass floor rises as a shape gets more common and when two sites
share nothing but their shape. A fragment ten or more files repeat with shared
names is one low-confidence `convention` finding. With git, a clone whose files
both change more than the typical file is called out: one copy gets fixed, the
other drifts.

## Design smells

RuboCop measures one method at a time; these are about how objects treat each
other. Each is reported only where its advice applies to code the project owns.
All are on but `repeated_conditional`, `middle_man` and `boundary_sprawl` (see
[which kinds are on by default](#which-kinds-are-on-by-default)), and
`stateful_mixin`, which waits for [strict](#strict).

<!-- example: smells lib/app --kind smells -->
```console
Findings (3):
  data_class: Item holds 'base', 'tax', 'quantity' and does nothing else (item.rb:1). Move the code that works on these fields into the class.
      · base
      · tax
      · quantity
  feature_envy: Cart#price refers to 'item' more than to self, 3 to 1 (cart.rb:7). The behavior may belong on Item.
      · item (line 7)
      · self (line 7)
  control_parameter: Cart#print is steered by 'quoted' (cart.rb:9). Split the method, or pass a strategy instead of a flag.
      · quoted (line 9)
```

- **feature_envy** — a method refers to another object more than to itself.
  The advice is to move it onto that object's class, so hashira must be able to
  name the class and see that it owns it: from a constructor (`Widget.build`,
  `Widget.new { |w| }`), a rescue clause or a type test (`is_a?`, `case`/`when`,
  `case`/`in`, a table keyed by classes); only where none of those says
  anything, from the variable's name or last words, and then only when they
  name an owned class in sight of the method, as Ruby would resolve them
  (`item` is the `Item` beside the method's class, `base_dir_config` a
  `Config`), never a same-named class elsewhere, never the method's own class
  and never a core class (`range`, `set`). A type test on a library class
  (`when Prism::ConstantPathNode`) outranks the name. That class, with
  its owned superclasses and mixins, must declare every message the method
  sends it (what every object answers, `to_s`, `nil?`, aside). A class whose
  ancestry leaves the project (an ActiveRecord model) also answers what its
  library and schema define, so for it only the messages the codebase itself
  defines somewhere must be declared. A parser node, a source range or an array is not envied. Comparators,
  mappers that only copy fields into a hash or a constructor, and methods that
  fill a role peers share stay quiet.
- **control_parameter** — an argument used only to pick a path, where some
  caller passes it as a literal flag (`true`, `false`, a symbol) by position or
  keyword. A caller counts only when its receiver is the method's class: a bare
  or `self` call inside it, the class itself (`Database.build(:pg)`), an object
  it builds (`Cart.new`, a local assigned one), a variable named for it
  (`@cart` is a `Cart`), or a literal of a core class the project reopens
  (`"x".camelize(:lower)`). A same-named method elsewhere (`@items.build(:line)`)
  is not evidence. An argument that callers compute, a configured style, an
  argument a branch only maps to a value (`flag ? "on" : "off"`) or to a built
  object (a factory: `name == "pg" ? Postgres.new : Null.new`), and one compared
  with another value are data. Only a method callers outside the class can reach
  counts: a private or protected helper's flag sits behind the explicit public
  methods that call it.
- **data_clump** — the same three or more parameters travel together through
  three or more methods, one handing the group to another.
- **repeated_call** — the identical call made twice in one method; name the
  result. One finding per class, with every repeated call and its method as
  evidence ("repeats 14 calls in 6 methods"). Chains that share a repeated
  prefix count once, as the prefix (`qm.message × 5` for `qm.message.scope`,
  `qm.message.rcpt_to`, …), since one local fixes them all; an index read
  shows as written (`params[:user]`). Identity is by value: a local counts by its binding, a literal block is
  part of the call, a reassignment between makes two values, and `__LINE__` is
  the line it is written on (`__LINE__ + 1` on two lines is two values). Left alone: calls
  that mint a fresh value (`dup`, `rand`, `SecureRandom.hex`), a read that
  draws the next item from a stream or a queue (`io.gets`, `getc`,
  `readpartial(n)`, `recv(n)`, `queue.pop`, `args.shift`; not `read` or
  `File.readlines(path)`, which a file answers alike twice), a command whose
  result is thrown away, two reads no single run reaches both of (`return`,
  `raise` and the `render :index and return` idiom end a run; `x or return`
  is a guard the run passes), a read after a
  command on the receiver, or after a call on self whose method (or one it
  calls on self) sends the instance variable read a message as a command or
  as its own answer, but a predicate or that same reader, or reassigns it
  (`start = @scanner.pos; token; @scanner.pos` with `def token =
  @scanner.scan(…)`), a reading measured by distance or order against a
  stored copy of its own earlier result (`started = clock.now; ...; clock.now -
  started`, a deadline loop, also one that names each reading as it compares
  it, `while (now = clock.now) < deadline`), and a plain read of self, a local or an instance
  variable — no arguments, or literal keys — made at most twice in any one run,
  which is style; a reader the class declares (`attr_reader :options`) reads
  its instance variable, so `options[:routing]` twice is `@options[:routing]`
  twice. A chain (`order.customer.address`), a helper method's result
  (`settings[:a]`, a framework's `params[:id]`),
  a constant's query (`Time.now` twice is two times) or three reads in one run
  are reported.
- **repeated_conditional** — one class testing the same condition in three or
  more places: a comparison with a fixed value (`@mode == :draft`), a type test
  (`is_a?`), or the subject of a `case`; polymorphism is overdue. A plain truth
  test (`signed_in?`, `@closed`) asks about state rather than dispatching on
  it, and stays quiet.
- **state_sprawl** — a class whose fields weigh more than four. A field the
  constructor takes straight from an argument (`@size = size`, or
  `@w, @h = w, h`) is an input, a component's props or a job's arguments, and
  weighs nothing. Any other field the constructor (or a helper it calls, or a
  callback the class registers such as a `before_action`) sets weighs one. One
  set elsewhere (a method, or an `attr_writer`/`attr_accessor`, which a caller
  or ActiveModel's attribute assignment fills) and taken up by another method
  or a reader is parked between calls and weighs two; one set elsewhere that
  no method reads is handed on —
  to a template, to a caller — and weighs nothing. Memo caches (`@x ||=`,
  `@_x`, `defined?` guards) are not state, and a class whose methods use all
  its constructor fields together is one handle.
- **assumed_state** — an instance variable read that nothing the class can reach
  ever assigns: a typo, or a fragile base class waiting for subclasses to install
  its state. Assigning counts wherever Ruby does it on the instance: a method,
  an attribute writer (also one minted from a list the class declares,
  `attr_accessor(*OPTIONS)`), `instance_variable_set` (a computed one,
  `instance_variable_set("@shop_#{key}", v)`, anywhere in the class or its
  ancestors and whatever method reaches it, assigns every read that starts with
  its literal prefix), and a block the class body hands its own DSL
  (`start { @mode = :text }`, `before_action { … }`), which the framework runs
  on the instance. A literal `instance_variable_set` on an instance any method
  in the project builds of the class assigns too, through a local
  (`params = new(v); params.instance_variable_set(:@nesting, n)`) or a `tap`
  (`DSL.new.tap { |dsl| dsl.instance_variable_set(:@context, c) }`). A class
  whose ancestry runs through a class the project only reopens under a
  dependency's root (`class Tilt::Template; include Safe; end`) is not judged,
  as with a parent it cannot see. A class whose code holds a string hashira cannot read (an `eval` or
  `class_eval` string, an x-string, `binding`) may assign anything, so it is
  never judged, and a `def` nested in a method (inside
  `::ActionController::TestCase.class_eval do … end`) is another class's.
- **utility_function** — a public method of a class that touches no instance
  state. A module's methods (a mixin, a concern, a view helper) lend behavior
  and stay quiet. A method that fills a role its kin define (`perform` on every job, a hook a
  library calls, even one whose name the project sends a class as a macro,
  `validate :paired` beside a validator's `validate(record)`, an override of a method a core ancestor defines such as an
  error's `message`, even where the project sends that message too, a fake's
  side of a protocol: `Fake`, `Mock`, `Stub`, `Null`,
  `Dummy`, `*Double`; the classes one array literal builds side by side,
  `[HelpSection.new(user), FeedexSection.new(user)]`, or one hash literal
  holds as its values, built or as a table of classes to pick from,
  `FORMATS = { plain: Plain, json: Json }`) is exempt. So is what
  Ruby asks of every object, at the arity it asks it (`==`, `eql?`, `equal?`,
  `<=>`, `===`, `coerce` taking one argument; `hash`, `inspect`, `to_s` taking
  none): a null object's `eql?` answers without state, and Hash, `sort` and
  `p` call it whatever its body reads. So is a method whose body holds code
  hashira cannot read: an x-string (`` `self.write_proc(s)` ``, `%x{}`), an
  `eval`/`class_eval`/`instance_eval`/`module_eval` string, `binding` or
  `local_variables` may touch any local, instance variable or method in scope.
  A hook's name is the project's own only where it goes to `self`, to an
  object of the class's own lineage or to one hashira cannot type: sent only
  to another class's objects (`ListPublisher.new(tag).perform` beside a
  Sidekiq job's `perform`) or spelled as a hash key (`save!(validate:
  false)`), it stays the library's.
- **manual_dispatch** — a `respond_to?` probe, or a `case`/`is_a?` ladder over
  two or more of the codebase's own classes or the object's own status. The
  probe must be on self or on an object whose owned class can be named (a value
  of unknown type is never taken for the method's own class), and ask for a
  message the codebase defines, which a computed message never is. Where the
  receiver's only type evidence is its name (`template` read as
  `Shop::Template`), the probe is the codebase's only if that class or its
  family answers the message; otherwise it is a duck test on something else.
  Ruby's protocols (`:each`, `:to_hash`, …),
  `respond_to_missing?` and the `method_missing` it pairs with are exempt, and
  so are the comparison protocols (`<=>`, `==`, `eql?`, `===`, `equal?`,
  `coerce`), which must take any object and answer for what they were handed.
  The same type test on the object's own state in three or more methods of one
  class (`@check_in_target.is_a?(Event)` in six actions) is a switch spread
  over methods: one finding for the class, each site as evidence.
- **nil_check** — `nil?`, `== nil`, `when nil`, `blank?`, and, on a value the
  code itself leaves nil, `&.`, `unless x` and `x || default`. Reported only
  where the nil is the codebase's own: its state, a nil it assigns, its own
  method's result (not a reader that answers a literal or memoizes one, `def
  successors = @successors ||= {}`, which never answers nil), a private
  method's argument, a literal it built, a record fetched from an owned class,
  or an attribute an owned class declares. Under `strict: true` it also takes a
  parameter the method defaults to nil, and the answer of another owned class's
  method that can answer nil (its body ends in `detect`, `find`, `first`,
  `last`, `[]`, `dig`, `min_by`, `&.`, a literal `nil`, an `if` or `case`
  without `else`, or it returns early with nothing), reached through an
  instance variable or local named for that class or an object built on the
  spot (`Finder.new(rows).parent(id)`).
  A public method's argument, a payload read from outside and a library's
  answer (a node's absent receiver, a URI's missing scheme, Ruby's answer to a
  core value an owned constant holds: `PATTERN.match(path)` with `PATTERN =
  %r{…}`) are someone else's contract. A validator's guard on an attribute a presence validation already
  reports, a check replaced by its default, a check whose branch raises, itself
  or through a method of the class that always raises (its last statement
  raises and it never returns early: the guard asserts against the nil),
  memoization in any of its spellings (`@x ||= v`, `@x = v unless @x`, `@x = v if @x.nil?`, an `else` that only answers
  `@x`, a fill whose last statement writes `@x`, `return @x unless @x.nil?`
  before the fill), and a one-line predicate that
  answers a nil test (`def adapter_set? = !@adapter.nil?`) stay quiet. By
  default a parameter defaulting to nil is the caller's option, not the
  codebase's nil; under `strict: true` one the method tests (`def
  discounted(coupon = nil)` … `coupon.nil?`) is an optional argument, two
  methods in one, and is told to split the method or ask for a null object:
  Elegant Objects accepts no nil arguments. A predicate that fetches
  a record only to test it for nil is told to ask `exists?`. Checks of one
  nil source — an instance variable, a method that can return nil — are one
  finding, named for the source (`Account@owner`, `Account#current`,
  and, under strict, `Catalog#find` for `item = @catalog.find(code)` checked
  in `Cart`), with
  each method that checks it as evidence: settle it where the nil is made.
- **boundary_sprawl** — twelve or more methods across three or more files
  type-testing against one foreign root (`Prism`, `ActiveRecord`): a missing
  adapter. A program that interprets a foreign model on purpose can declare it
  (see [CI](#ci)). A constant a namespace takes from elsewhere counts as the
  one it came from: `const_set(name, Prism.const_get(name))` copies Prism's,
  and `Node = Parser::AST::Node` aliases Parser's.
- **module_initialize** — `initialize` in a mixin: constructor state carried
  into every includer. A module that extends itself (`extend self`) is no
  mixin and has no includer: its `initialize` is an ordinary method, and the
  module-level state it sets is kata's to report.
- **stateful_mixin** (strict: on only under `strict: true`) — a mixin whose
  behavior works on its host's state rather
  than through the host's public methods: its methods read an instance
  variable nothing in the module assigns (the host's `@text`; what the module
  assigns itself counts even when it extends or includes a module hashira
  cannot see, `extend Forwardable`), keep state of
  their own in the host (`@events = …`), or it installs fields, associations,
  callbacks or validations on the host (`included do after_save :track end`,
  `base.validate`, `attr_accessor`). Elegant Objects composes decorators
  instead: wrap the host and reach it through its public methods. One finding
  per module, each field or hook as evidence. Left alone: a protocol mixin
  that calls only its host's public methods (`Comparable`'s `<=>`), memo
  caches (`@x ||=`, `@_x`), a module that is not a mixin (`extend self`,
  `module_function`, a refinement), and one whose code holds a string hashira
  cannot read.

The next six judge how classes are built. They need the class to be the
project's own, so a framework's base classes stay out of all of them.

- **concrete_inheritance** — a class extends an owned class that the project
  also builds on its own (`Report.new` somewhere, or a bare `new` in the
  parent's class methods): the subclass is coupled to a working
  implementation, not to an abstraction. One finding per parent, named for it
  and sited at its definition, with every subclass and the places that build
  the parent as evidence. Left alone: a parent that says it is abstract (named
  `Base` or `Abstract…`, a method that only raises `NotImplementedError` or
  `NoMethodError`, `abstract_class` or `abstract!`), a parent nothing builds
  directly, and, by default, any hierarchy whose owned root extends something the project
  does not own (`ApplicationRecord < ActiveRecord::Base`, `MyError <
  StandardError`, `Struct.new(…)`). Under `strict: true` such a hierarchy is
  judged too: there a framework builds the objects, so a subclass counts when
  it overrides a working method of its concrete parent (single-table
  inheritance's `Stripe::Charge#sync!` over `Charge#sync!` is a strategy the
  record should be given), each overriding method as evidence, while one that
  only adds to its parent (scopes, validations, `store_accessor`, methods of
  its own), only gives itself a constructor, or overrides a hook the parent
  leaves empty or a method it refuses (`refused_bequest`'s business) is left
  alone. Strict also reports a class that extends a concrete core collection
  or value (`Array`, `Hash`, `String`, `Set`) on its own: what it inherits
  (`map`, `select`, `merge`) answers a plain core object, so hold one in a
  field instead. And it reads a `Base…` parent (`BaseController`) as
  abstract, like `…Base`.
- **refused_bequest** — a subclass overrides a method an owned ancestor
  implements, only to raise or to do nothing (an empty body or a bare `nil`).
  One finding per refused method, named for it (`Questionnaires::Base#next_step`)
  and sited at its definition, with every refusing subclass as evidence.
  Left alone: overriding a hook the ancestor itself leaves empty or
  unimplemented (that is filling a template, not refusing it), an override
  that calls `super` or does anything else, and a library parent's methods,
  whose contract is not the project's to redesign.
- **low_cohesion** — LCOM4: a class of six or more methods (constructor aside)
  whose methods fall into two or more groups that share no instance variable
  and never call each other, each group holding two or more methods and a field
  some method reads. Readers, writers, `def_delegators :@field` and
  `delegate :name, to: :field` count as touching their field; `send(:name)` and `method(:name)` count as calls, and a
  computed `send("matches_on_#{name}?")` calls every method its literal parts
  spell, as dead_code reads it; one that spells a writer (`send("#{name}=",
  value)`, a mass assignment) calls every writer, hand-written or minted by
  `attr_writer`/`attr_accessor`, and so touches their fields. A method that reads fields by computed name
  (`instance_variables`, `instance_variable_get(ivar)`), in the class or in a
  module it includes, may touch any of them and joins every group (caxlsx's
  `SerializedAttributes` writing one XML element's attributes). The
  constructor joins what it ties together statement by statement: a field it
  derives from another group's method (`@rules = load_rules`) or from the same
  argument as another field. Left alone: a field only written (handed to a
  template), a lone stateless method (that is `utility_function`'s business),
  modules, and classes under a framework base, whose controllers and mailers
  split into independent actions by design. Under `strict: true` that
  exemption narrows to the presentation stratum — controllers, mailers, jobs,
  channels and mailboxes, by name or by the framework base they extend — and a
  model is judged like any class: hashira does not read the schema, so its
  columns count as fields in every spelling a model touches them: a bare call
  or a call on `self` to a name the class does not define (`state`,
  `self.state`, `self.state = …`, `self.count += 1`), and the column a
  persistence call names (`update_column(:state, …)`, `update_attribute`,
  `write_attribute`, `read_attribute`, `self[:state]`, the keys of
  `update(state: …)`, `update_columns` and `assign_attributes`). A Kernel
  method called bare (`raise`, `binding`) is not a column, and a reader
  `delegate`d to an association is that association's field. An association
  and the columns that back it are one field: `parent_id` (or its
  `foreign_key:`, and `parent_type` when polymorphic) is `belongs_to
  :parent`'s, and a `through: :lists` association is `lists`'s.
- **message_chain** — the Law of Demeter, on one chain: `order.customer.address`
  calls a method on what an owned object's reader returned. Every link must be
  typed and owned: the start (a parameter, local, instance variable or own
  reader) is named for an owned class, that class declares the reader, the
  reader is named for another owned class, and that class declares the next
  message. The evidence shows the classes crossed (`Order → Customer`). Left
  alone: a library's objects (`node.loc.selector`), core collections
  (`items.first`), a hop with arguments or a block (builders, queries), a hop
  back to the same class (fluent APIs), a Struct or Data value's readers, and
  messages every object answers (`to_s`, `==`). Chains through the same two
  classes are one finding (`Order → Customer`), with each method that reaches
  through as evidence. This is separate from `repeated_call`, which reports a
  chain read twice whatever its types.
- **data_class** — a class with two or more fields and nothing but attribute
  macros, hand-written readers and writers, and a constructor that only stores
  its arguments. Left alone: `Struct` and `Data` (a value declared as one), a
  class with a superclass or a subclass (an error carrying a code, a base
  others extend), and any method, mixin, class method or constant. Under
  `strict: true` a declared value is one too when another class computes with
  it: a `Struct` or `Data` value with nothing but its members (`Address =
  Struct.new(:street, :city, :zip)`, `class Size < Struct.new(:w, :h)`), or
  an ActiveRecord model with no methods, callbacks or validations of its own
  (only associations, scopes, enums and attribute declarations), once a method
  of another owned class reads two or more of its fields from one object
  (`Invoice#total` multiplying `@order.quantity` by `@order.unit_cents`): the
  logic about the data lives away from it, so nothing keeps its meaning. One
  finding per value, each method that computes with it as evidence. Left
  alone there: a value or record with behavior of its own, a value nested in
  the class that reads it (that class's own record), and fields copied into a
  constructor (`Part.new(part.slug, part.title)`), which is mapping, not
  computing.
- **middle_man** — a class whose public methods mostly (more than half, and at
  least three) only forward to one field: one call on an instance variable or
  its reader, passing the method's own arguments, and its block if it takes
  one, through unchanged. A call given a block of its own
  (`@mutex.synchronize { @count += 1 }`) is doing the method's work there, not
  forwarding it. A single forwarder is left alone, since it is exactly what
  `message_chain` asks for.
  Left alone too: a class that declares its delegation (`def_delegators`,
  `delegate … to:`, `SimpleDelegator`, `DelegateClass`) — the declaration is
  the design, a wrapper that narrows an interface on purpose, and removing the
  middle man would mean giving that up — a decorator, whose every public
  method that does not forward wraps the same call on the same field
  (`def subject = "URGENT: #{@origin.subject}"` beside `body` and `recipient`
  passed straight through): wrapping is how Elegant Objects adds behavior, and
  the advice would undo it — forwarding to a collection's own
  protocol (`each`, `size`, `<<`: an encapsulated collection), a facade
  spread over several collaborators, and a method that fills a role its kin
  share.

Class-level kinds judge a class across every file that reopens it, and site
it at the opening in the file named for it (`shop/report.rb` for
`Shop::Report`), else at the opening with the most statements, the choice
rubocop-kata's `Kata/Reopening` makes. A `def`
inside a block handed to a call (a DSL such as rodauth's
`Feature.define(:change_login, :ChangeLogin) do … end`) is not the enclosing
module's: it belongs to the constant the call names by a CamelCase symbol or
string (`Rodauth::ChangeLogin`), or else to an owner of its own per block
(`Auth::(configure block, line 7)`); a refinement's is the module and what it
refines (`Ext refine ::String`). Blocks that reopen the class or build a new
one keep the enclosing owner: `included`, `class_methods`, `concerning`,
`class_eval` on self, Thor's `no_tasks`/`no_commands`, `helpers` in a class
whose superclass is Sinatra's or Padrino's, `Class.new`, `Module.new`,
`Struct.new`, `Data.define`. A block a constant evaluates
(`Rack::Request.class_eval do … end`) belongs to that constant. The design
smells name a concern's class-level methods for the concern with a dot
(`Searchable.search`), from `class_methods do` or from a `ClassMethods`
module its namespace hands its host or takes itself (`extend
ActiveSupport::Concern`, an `included` block, `base.extend` in
`self.included`, or `extend ClassMethods`); any other
`ClassMethods` module keeps its own name (`Ancestry::ClassMethods#tree_view`),
and a `def self.` inside one is that module's (`Ancestry::ClassMethods.check!`).

## Hotspots

The rollup charges each file its methods' cognitive complexity and the distinct
nodes its clone sites cover, and multiplies by how many commits touched it:

<!-- example: duplication app --kind duplication -->
```console
Hotspots — cost alone, no git history to weigh (where refactoring pays the most):

file                Cog  Dup  Churn  Rank
-----------------------------------------
reports/orders.rb     0   38      0    38
reports/payouts.rb    0   38      0    38
reports/refunds.rb    0   38      0    38
```

Read it as a work queue. The rank counts churn as at least one, so a
repository without history ranks by cost alone, and the heading says so; a
shallow clone or a single commit counts as no history. It is deliberately not a grade: a letter on a healthy
codebase is the same letter on every row.

## CI

`--fail-on` fails the build when findings of a kind exist at all (`cycles`,
`sdp` and `dupe` are shorthands; `smells` is every smell kind). `--fail-on all`
gates every kind the run checks: the default kinds, the ones `checks:` turns on,
less what `--skip` drops and narrowed to `--kind` when it is given. It turns no
opt-in kind on by itself. That is the gate for a codebase at zero findings, with
no baseline to keep:

```sh
hashira --fail-on all            # fail on any finding this run reports
```

It suits a codebase that starts clean. The **ratchet** suits every other one:
record what is true now, and fail when it grows.

```sh
hashira --update-baseline        # record today's edges and findings
hashira --ratchet                # fail if either set grew, or a finding got worse
```

A finding with a size — cognitive score, clone mass, sprawl count — is recorded
with it, so a baselined method that gets more complex fails:

<!-- example: ratchet lib/shop --ratchet -->
```console
WORSE FINDING (was 9, now 11):
  complexity: Shop::Pricing#total — cognitive 11, 14 calls (pricing.rb:3). flatten the branching — guard clauses, early returns, or polymorphism.
...
Ratchet FAILED. Either fix what regressed, or — if it is deliberate —
record the decision: update the baseline, or accept it with a reason.
```

and a new one prints in full:

<!-- example: fresh app --ratchet -->
```console
NEW FINDING:
  duplication: 3 similar fragments (mass 38) — differs only in literal values — extract a method, pass them as arguments.
      · reports/orders.rb:4-8
      · reports/payouts.rb:4-8
      · reports/refunds.rb:4-8
```

The baseline also records a trace of each finding (its file and wording,
without line numbers), so a renamed method keeps its finding instead of
reporting one resolved and one new. It records which kinds the recording
hashira knew: after an upgrade adds a kind, its findings are listed as not
ratcheted until the baseline is refreshed, instead of failing the build.
Baselines from earlier versions read compatibly, kinds renamed since included.

`--only FILES --ratchet` asks, from an editor or a pre-commit hook, whether the
files you touched got worse. The whole project is still read — half of what
hashira knows is cross-file — and only the report is narrowed; edges and
removals are left to the full run.

Exit codes: `0` clean, `1` findings or a regression, `2` misuse (bad flags, a
missing directory, an unusable baseline), `3` an improvement the baseline has
not recorded yet, `70` an internal error.

**Accepting by design.** A deliberate finding goes in the baseline with a
reason, and leaves reports and gates:

```json
"accepted": [
  {"kind": "complexity", "package": "Legacy::Importer#run", "reason": "vendored, rewrite scheduled"},
  {"kind": "duplication", "digest": "8bbddea787bc", "reason": "generated adapters, regenerated together"}
]
```

A clone is named by the `digest` of its shape (read it from `--json`), which
survives the lines above it moving.

**Declaring an interpreted model.** A compiler interprets an AST; a serializer a
schema. Instead of accepting a `boundary_sprawl`, declare the boundary, and
hashira checks the declaration: the root must be called, and only through the
named entrypoint.

```json
"boundaries": [
  {"root": "Prism", "role": "interpreted_model", "entrypoint": "lib/my_tool/trees.rb", "reason": "the Prism AST is the input model"}
]
```

A declaration is structure, not debt, so it can live in `.hashira.yml` instead,
where a codebase with no baseline keeps it (both lists apply when both exist):

```yaml
boundaries:
  - root: Prism
    role: interpreted_model
    entrypoint: lib/my_tool/trees.rb
    reason: the Prism AST is the input model
```

## Other formats

```sh
hashira --json            # every finding and row; --top N caps the lists
hashira --json --compact  # one line, for piping
hashira --format dot      # Graphviz
hashira --format mermaid  # Mermaid
```

The JSON opens with `version`, `packaging`, `targets` and `files`, then
`findings` (each with its `digest` and `confidence`), `kinds` (count and files
per kind), `suppressed`, `unused_suppressions`, `accepted`, `packages`, `edges`,
`folds`, `complexity`, `duplication` and `hotspots`. A package with no edges
reports `"i": null`. Confidence is `high` for measurements (complexity, the
structural kinds, clones differing in a literal, receiver or constant), `medium`
for smells, fragmentation, indirection and looser clones, and `low` where
hashira hedges (clones whose control flow differs).

## Design choices

- **Cognitive complexity, not call counts.** Older Ruby metrics charge a point
  per message send, so a flat method calling twenty collaborators outranks a
  knotty one, and a Rails model's column of `has_many` lines tops the list.
  Cognitive complexity makes straight-line code free and nesting expensive.
- **No abstractness, no main-sequence distance.** Those assume formal
  interfaces; idiomatic Ruby decouples by duck typing, so the measure pins to
  zero and restates instability.
- **Ruby files only.** Templates are out of scope. Comments are read only for
  `hashira:` directives.
- **Text is read as UTF-8.** A file is decoded from the encoding its magic
  comment declares, and bytes no encoding reads (a binary file's high bytes, a
  stray byte, a literal's `"\xFF"`) read as U+FFFD, so one odd file never stops
  a run.
